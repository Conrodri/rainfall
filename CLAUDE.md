# Rainfall

Survivor-like 2D **vue de dessus**, mobile (Android puis iOS) **en paysage forcé**, base 1920×1080. Godot 4.7.2 (GDScript, renderer Mobile).
Inspiré de Vampire Survivors x Risk of Rain 1/2. Les guides font foi : `docs/GDD.md`, `docs/Maths_Scaling.md`, `docs/Items_Catalog.md` (+ `.xlsx`), `docs/simulateur_scaling.py`. Le nom de travail « Ember Run » des guides = **Rainfall**.
Langue : français (docs, commentaires, textes du jeu). Identifiants de code en anglais.

## Décisions
- **Plateformes : PC (Windows), Android et iOS.** Chaque fonctionnalité doit marcher sur les trois : entrées tactiles ET clavier/souris ET manette ; contrôles tactiles (joystick, boutons) masqués sur PC sauf écran tactile ; pas de bouton Quitter sur iOS ; pubs et achats derrière une couche abstraite (absents ou remplacés sur PC).
- **Paysage partout** (décision du joueur, 21/10/2026) : téléphone forcé en paysage (capteur paysage, les deux sens), PC en paysage redimensionnable ; base logique 1920×1080 `keep_height`. Le HUD et les menus restent adaptatifs au ratio (aucune position codée en dur).
- **Contrôles PC** : déplacement ZQSD/WASD/flèches ou stick gauche ; sort 1 automatique partout ; **sur PC les sorts 2-4 visent le curseur de la souris** (clic gauche/droit + touches), à la manette ils visent avec le stick droit (sinon l'ennemi le plus proche) ; sur mobile ils gardent le ciblage automatique.
- **Caméra isométrique façon Dofus (décision du joueur, 21/10/2026)** : projection dimétrique 2:1, vue tournée à 45° (sol en losanges, murs en diagonale), élévation 30°, recul ~20-30 % de terrain en plus qu'avant. Migration planifiée dans docs/Design_Isometrique.md ; tout nouvel asset Blender se rend avec cette caméra. Rythme visé (vidéo de référence) : monstres de base fauchés en 1-2 coups, petits paquets de 3-8, déplacement rapide.
- **Performance et ombres cuites (joueur, 21/10/2026)** : le jeu doit rester léger (mobile d'abord). Ombres des éléments statiques cuites (dans les sprites par Codex : AO + décalques `<f>_shadow.png` ; dans Godot : couche d'ombres précalculée au chargement de l'étage), ombres dynamiques limitées et plafonnées par palier ; modèles Blender au polycount utile, PNG optimisés (art/briefs/STYLE.md « OPTIMISATION ET OMBRES CUITES »).
- **Structure des étages façon RoR2 (joueur, 21/10/2026)** : l'étage N a toujours le même biome (même DA), tiré parmi 2 variantes de carte ; étages 1-4 = 4 biomes ; étage 5 = étage de boss final, sans variante. Par étage : au moins 3 boss d'étage différents et 5 mini-boss. Tous dans la DA d'ash_lord (lot R8a, validée), déclinée par biome (thème, colorimétrie, accent émissif). Plan : docs/Design_Etages.md. Tranché : étage 4 = Cryptes noyées, étage 5 = « La Source » avec un boss final unique à 3 phases, run ≈ 18-20 min, étages 4-5 produits avant les variantes B.

## Orchestration
- **Fable = orchestrateur** (session principale, `/model fable`) : découpe, contrats, lancement d'agents **en parallèle au maximum**, intégration, vérification.
- **Fable (agent)** : game design créatif, boss, cartes, direction artistique.
- **Opus** : systèmes complexes et critiques (director, performance 250 monstres, sauvegarde, architecture), revues de code.
- **Sonnet** : implémentation de fonctionnalités, UI, pilotage de Codex pour les assets.
- **Consultants design** (`.claude/agents/`, 22/10/2026, adaptés de Claude-Code-Game-Studios, MIT) : `game-designer` (Fable : boucles, combat, ressenti, kits), `systems-designer` (chiffres : formules, items, or, scaling ; skill `/balance-check`), `level-designer` (cartes, rythme d'étage, placements), `ux-designer` (HUD, menus, entrées, accessibilité). Ils ne codent pas : avis avec options, recommandation chiffrée, sources. Les lancer en parallèle sur une même question puis croiser.
- **Mode ultracave pour TOUS les agents (joueur, 23/10/2026)** : chaque agent lancé (y compris en parallèle, tous types, Codex compris) écrit ses messages et son rapport en style ultracave (`~/.claude/skills/ultracave/SKILL.md`). Règle déjà en fin de `.claude/agents/*.md` et dans `art/tools/_codex_eco.txt` ; pour tout autre type d'agent, la mettre en tête du prompt. Fichiers persistés (code, docs, briefs) en prose normale.
- **Haiku** : tâches mécaniques rapides (conversion de données, renommages, vérifications, recherche).
- Un agent ne modifie **que les dossiers qui lui sont attribués** ; les fichiers partagés (`project.godot`, `scripts/core/*`, `scenes/main.tscn`) sont réservés à l'orchestrateur. Un besoin de contrat nouveau = le signaler dans le rapport final.
- Blender est une seule instance : **un seul agent d'assets à la fois**. Ne jamais modifier un .blend hors de `art/blender/` (ex. projet PeakSurvivor).

## Contrats (autoloads)
- `Events` (`scripts/core/events.gd`) : bus de signaux (enemy_killed, player_damaged, pickup_collected, chest_opened, item_chosen, boss_*, pillar_state_changed, floor_*).
- `Balance` (`scripts/core/balance.gd`) : formules pures du doc Maths (difficulté, director, monstres, boss, joueur, stacking, coffres, rubis).
- `RunState` (`scripts/core/run_state.gd`) : temps actif, étage, mode, or, XP, niveau, items {id: stacks}, pity, rng ; `difficulty()`, `add_gold/spend_gold/add_xp/add_item/stacks`.
- `InputSetup` : actions move_left/right/up/down, aim_left/right/up/down, spell_2..4, interact, pause (clavier physique, manette, souris hors tactile).
- `Platform` : plateforme et mode d'entrée courant (voir game/CONTRACTS.md).
- Groupes : `player`, `enemies`, `pickups`, `chests`. Couches physiques : 1 world, 2 player, 3 enemies, 4 player_projectiles, 5 enemy_projectiles, 6 pickups, 7 interactables.
- Placeholder : tant qu'un sprite n'existe pas, formes colorées (Polygon2D / `_draw`) ; l'échange contre un sprite ne doit toucher qu'un nœud visuel.
